# ADR 0001 — Terminal composition model

- **Status:** accepted
- **Date:** 2026-07-28
- **Deciders:** Spike A
- **Evidence:** [docs/spikes/terminal-embedding.md](../spikes/terminal-embedding.md)

## Context

The session view has to show a live terminal running Claude Code inside a Tauri
window. The architecture plan named three candidate compositing models and made
picking one the deliverable of Spike A:

1. a native child surface (NSView / HWND / GTK child) hosting ghostty's own
   renderer;
2. ghostty rendering offscreen into a texture composited by the webview;
3. libghostty as VT state only, with a renderer we write.

The plan preferred 1, expecting the trade to be fidelity against integration
pain. It also set a kill criterion: if nothing clears the latency and stability
bar, ship xterm.js instead.

Spike A established from Ghostty's source at
`a60cd15bb5a197d8e2596e86442031cbece06bcc` that the choice is narrower than
assumed. Ghostty ships two C libraries. The GUI embedding API in
`include/ghostty.h` — the one that owns the GPU renderer — accepts only an
AppKit `NSView` or a UIKit `UIView`; `ghostty_platform_u` has no GTK, X11,
Wayland, or Win32 member, and on non-Apple targets surface construction returns
`error.UnsupportedPlatform`. Ghostty's own Linux GTK4 UI is an internal Zig
`apprt` with no C entry point. The cross-platform library, `libghostty-vt`,
provides VT parsing, terminal state, incremental render state, and input
encoders — but deliberately no renderer.

So on Linux, models 1 and 2 are not available. Not "hard": absent.

## Decision

**Use `libghostty-vt` for terminal state and input encoding, and render it
ourselves into a native surface that is a sibling of the webview — not an
overlay.** On Linux that surface is a GTK3 `DrawingArea` drawn with Cairo and
Pango. This is model 3.

The terminal crate stays free of Tauri and of any GUI toolkit; the renderer
lives in the harness. Raw PTY bytes are tee'd to a separate event stream for
transcript capture and are never part of the rendering path, and never enter
the webview.

Use the same model on macOS initially, rather than the AppKit embedding API,
so there is one renderer and one code path. Revisit only if macOS typography
proves inadequate — see the spike notes, section 6.

## Consequences

**Accepted.**

- **Webview UI may not overlap the terminal region.** A native sibling widget
  is not in the webview's layer tree. Modals, tooltips, and panels must avoid
  that rectangle, or be native themselves. The architecture plan predicted this
  constraint and flagged that it hardens the UI design; it is now real.
- **We own the renderer:** font selection and fallback, ligatures, glyph
  caching, and any future Kitty graphics support. Ghostty's GPU renderer, atlas,
  and shaping are unavailable to us on Linux.
- **The dependency is pre-1.0 and documented as unstable.** Pinned to an exact
  commit; upgrades are deliberate. Bindings are generated by bindgen from the
  installed headers, so an upstream signature change is a compile error rather
  than undefined behavior.
- **Tauri v2 on Linux is GTK3**, so the surface is a GTK3 widget even though
  Ghostty's own Linux UI is GTK4. Mixing generations in one process is not an
  option.

**Gained.**

- Ghostty's VT correctness: scrollback, reflow on resize, wide characters and
  graphemes, and mode-dependent input encoding. Measured: once an application
  negotiates the Kitty keyboard protocol, Escape becomes `CSI 27 u` and Ctrl-C
  becomes `CSI 99;5 u`. Claude Code negotiates it, so a hand-rolled key map
  would be wrong in a way users would feel.
- Measured p50 input-to-glyph latency of 1.71 ms and 10.3 MiB/s sustained
  output with zero dropped bytes, on a headless VM with no GPU.
- The terminal crate runs as a standalone binary with no display server, which
  keeps it testable and the composition model replaceable.

## Alternatives rejected

**Native child surface hosting ghostty's renderer (model 1).** Impossible on
Linux: no C entry point accepts a GTK widget. Available on macOS, and deferred
there to avoid two renderers.

**Offscreen render into a webview texture (model 2).** Same blocker — reaching
ghostty's renderer at all requires the AppKit-only surface API. Would also add a
per-frame copy to a latency budget that is already fine.

**xterm.js.** The kill criterion was never approached: latency and stability
both passed comfortably. Choosing xterm.js would give up Ghostty's VT
correctness to solve a problem we do not have. The `TerminalSurface` boundary
keeps it available as a fallback.

## Revisit if

- macOS typography with a hand-written renderer is judged unacceptable — then
  take the AppKit embedding path there and accept two renderers.
- Upstream exposes a Linux surface in the GUI embedding API — then model 1
  becomes available and this ADR should be reconsidered.
- The UI design turns out to genuinely need overlapping panels over the
  terminal — then model 2 becomes worth its cost, but only on macOS, because
  model 2 is equally unreachable on Linux today.
